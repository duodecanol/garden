# 소프트웨어 공학에서 회귀(Regression)의 실무 의미

> [!abstract]
> 소프트웨어에서 **회귀(regression)**는 단순히 "과거의 나쁜 상태로 돌아감"이라기보다, **이미 정상으로 검증된 기존 baseline이 새 변경 이후 깨지는 현상**을 가리키는 실무 용어다. 결과로는 버그가 맞지만, "새 변경이 기존 동작을 망가뜨렸다"는 인과관계를 포함한다.

## 최종 정의

**Regression은 맥락이 붙은 bug다.**

- `bug`: 기대와 다르게 동작하는 결함 전체.
- `regression`: 이전에 정상 동작한다고 검증된 기능이, 이후의 코드 변경 때문에 깨진 경우.
- `regression risk`: 이번 변경이 기존 정상 동작을 깨뜨릴 가능성.
- `regression test`: 기존에 통과하던 동작이 여전히 통과하는지 다시 확인하는 테스트.

따라서 "회귀는 버그와 등가인가?"라는 질문에는 이렇게 답하는 편이 정확하다.

> [!note]
> 결과 현상은 버그가 맞다. 다만 모든 버그가 회귀는 아니다. 회귀는 "새 변경 이후 기존 baseline이 깨졌다"는 발생 조건을 가진 버그다.

## 문답과 사고의 흐름

### 1. 첫 문제 제기 - "회귀"는 그냥 에러나 버그 아닌가

출발점은 코드 리뷰 문맥이었다.

> [!quote]
> wrapper의 강제 소문자화가 사라지면 caller key와 catalog id가 case-exact 매칭으로 바뀐다. mixed-case 키에서 회귀 위험이 있어 cross-check 했다.

처음 질문은 이 표현 자체에 대한 의문이었다.

> [!question]
> "회귀"라는 표현은 무엇인가? "에러" 혹은 "버그"와 같은 말 아닌가?

초기 답변은 회귀를 "이전에는 잘 되던 기능이 코드 변경 이후 안 되게 된 현상"으로 설명했다. 이 정의 자체는 대체로 맞다. 하지만 "품질이 과거의 나쁜 상태로 퇴보했다"는 식의 설명이 붙으면서 의미가 조금 흐려졌다.

핵심 문제:

- "버그"는 포괄명이다.
- "회귀"는 변경 이후 기존 동작이 깨진 경우를 가리킨다.
- 그러나 "과거의 나쁜 상태로 돌아갔다"는 말은 실제 PR 현장을 설명하기에는 자주 부정확하다.

### 2. 두 번째 문제 제기 - 그러면 retrograde 아닌가

다음 질문은 단어 자체의 방향성에 대한 반박이었다.

> [!question]
> 과거의 나쁜 상태로 돌아가는 것이라면 regression보다 retrograde, 즉 퇴행이 더 맞지 않은가?

이 지적은 중요하다. `retrograde`는 방향 자체가 뒤집히거나 역행한다는 뉘앙스가 강하다. 반면 소프트웨어의 `regression`은 코드가 과거 버전으로 되감긴다는 뜻이 아니다.

정리하면:

- `retrograde`: 시스템이나 진행 방향이 뒤로 감.
- `regression`: 품질 기준선 또는 검증 상태가 이전보다 나빠짐.

다만 이 단계의 설명도 여전히 "예전의 결함 상태로 돌아간다"는 식으로 남아 있었고, 그래서 실무 감각과 완전히 맞지는 않았다.

### 3. 결정적 반박 - 새 PR이 잘 되던 기능을 새롭게 깨는 경우

가장 중요한 전환점은 다음 반박이었다.

> [!question]
> 실무에서는 새 PR이 멀쩡히 잘 돌아가던 기능을 처음 보는 방식으로 깨는 경우가 많다. 이것은 예전의 결함 상태로 돌아가는 것이 아니다.

이 반박이 최종 정의를 바로잡는다.

회귀는 반드시 "옛날에 고친 동일 버그가 다시 살아남"만 뜻하지 않는다. 현대 실무에서는 더 넓게 쓰인다.

- 과거의 동일 버그가 재발할 수도 있다.
- 새 변경이 기존 기능을 새로운 방식으로 깨뜨릴 수도 있다.
- 둘 다 공통점은 **기존 baseline이 새 변경 이후 깨졌다**는 점이다.

즉, 회귀의 핵심은 "과거의 특정 결함으로 복귀"가 아니라 "이미 통과하던 품질 기준이 새 변경으로 실패"다.

### 4. 왜 이런 용어가 굳었나 - Regression Test의 역사적 확장

초기 소프트웨어 QA에서 회귀 테스트는 실제로 "예전에 고친 버그가 다시 살아났는지 확인"하는 성격이 강했다. 그래서 `regression`이라는 말이 자연스러웠다.

하지만 시스템이 커지면서 기존 동작이 깨지는 방식은 더 다양해졌다.

- 동일 버그 재발
- 의존 코드 변경으로 인한 side effect
- 리팩터링으로 인한 호환성 파괴
- 데이터 normalization 제거로 인한 기존 데이터 불일치 노출

그럼에도 업계에서는 "기존 테스트 세트를 다시 돌려서 깨지는지 확인한다"는 QA 관점이 이미 `regression test`로 굳어졌다. 그 결과 `regression`은 "기존에 검증된 동작이 새 변경 이후 깨지는 현상" 전반을 가리키는 실무 용어로 확장됐다.

## 사례 분석 - lowercase 제거와 case-exact 매칭

원래 시스템은 wrapper에서 key를 강제로 소문자화했다.

```text
caller key -> lowercase -> catalog id와 비교
```

이 방식에서는 호출 측이 `UserKey`, `userkey`, `USERKEY`처럼 대소문자를 섞어도 내부적으로 같은 값처럼 취급될 수 있었다.

PR에서 이 normalization을 제거하면 비교 방식은 더 엄격해진다.

```text
caller key -> 원래 대소문자 유지 -> catalog id와 case-exact 비교
```

이 변경은 설계상 더 정확한 방향일 수 있다. 하지만 기존 데이터나 interpolation 결과가 mixed-case였고, 기존에는 lowercase 덕분에 우연히 매칭되던 상태였다면 새 PR 이후 매칭 실패가 발생할 수 있다.

이때 "회귀 위험"이라는 말은 다음 뜻이다.

> [!warning]
> 이번 변경 자체는 개선일 수 있지만, 기존에 정상처럼 동작하던 caller key 매칭을 깨뜨릴 수 있다. 그래서 배포 전에 catalog 데이터와 호출 측 key를 cross-check해 기존 baseline 붕괴를 사전 탐지한다.

## 내 언어로 다시 쓰기

코드 리뷰에서 `regression risk`를 더 직관적으로 풀어 쓰면 다음과 같다.

> 이 PR이 들어가면 기존에 잘 되던 동작이 깨질 수 있다.

조금 더 정확하게 쓰면:

> 이 변경은 case handling의 contract를 엄격하게 바꾸므로, 기존 데이터가 암묵적으로 의존하던 lowercase normalization을 잃어 매칭 실패를 만들 수 있다.

## 용어 선택 가이드

| 표현 | 언제 쓰나 | 뉘앙스 |
|---|---|---|
| bug | 기대와 다르게 동작하는 결함 전반 | 가장 넓은 표현 |
| error | 실패 결과나 런타임 오류 | 증상 중심 |
| regression | 새 변경 이후 기존 정상 동작이 깨짐 | 인과관계와 baseline 중심 |
| side effect | 변경의 간접 영향으로 다른 곳이 깨짐 | 원인 전파 중심 |
| retrograde | 방향 자체의 역행이나 퇴행 | 소프트웨어 QA 용어로는 덜 적합 |

## 보존할 결론

`Regression`을 "과거의 나쁜 상태로 돌아감"으로 설명하면 단어의 어원에는 가까울 수 있지만, 실무 감각과 어긋날 수 있다.

더 나은 설명:

> [!tip]
> 회귀는 "옛날 버그로 돌아감"이 아니라, "새 변경이 기존에 검증된 동작을 깨뜨림"이다. 옛날 버그의 재발은 그중 한 형태일 뿐이다.
