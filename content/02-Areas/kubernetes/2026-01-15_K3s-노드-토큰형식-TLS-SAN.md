# K3s 노드 운영 — 토큰 형식(K10 prefix) & TLS SAN

홈랩 구성을 위해 Ansible로 여러 머신에 K3s 클러스터 Bootstrapping을 자동화(IaC)하면서, 그리고 서버 인증서 SAN을 관리하면서 부딪힌 두 가지.

---

## 1. [Ansible/K3s] 토큰 포맷 삽질 (K10 prefix 주의)

### 상황
Master(Server)와 Worker(Agent)가 join하려면 **공유 Secret(Token)** 이 필요하다. 보통 보안을 위해 토큰을 사전에 지정해 배포하는데, 기존 서버에서 확인되는 토큰은 이런 형식:
```bash
$ cat /var/lib/rancher/k3s/server/token
K10ebc7694ce9cac44c72549bd7a03bed1dc9f375290b22929126e7699c8168ef2c::server:3ee51003c8b86d11d904ca84d28da7a5
```
"아, 이게 토큰이구나" 하고 이 전체 문자열을 그대로 `inventory.yml`/`group_vars`에 넣었다.
```yaml
# ❌ 잘못된 설정
k3s_token: "K10ebc7694ce9cac44c72549bd7a03bed1dc9f375290b22929126e7699c8168ef2c::server:3ee51003c8b86d11d904ca84d28da7a5"
```

### 문제
Worker 노드들이 Master에 join하지 못하고 **인증 실패(Authentication failed)** 혹은 타임아웃. 분명 서버 파일 내용을 그대로 긁어왔는데 왜?

### 원인: K3s 토큰의 구조
`/var/lib/rancher/k3s/server/token`의 전체 문자열은 두 부분으로 나뉜다:
> **형식**: `K10<CA_HASH>::server:<SECRET>`
- `K10<CA_HASH>`: 서버 CA 인증서 해시값. 클라이언트가 접속하려는 서버가 올바른지 검증하는 데 사용.
- `::server:`: 구분자.
- `<SECRET>`: 사용자가 설정하거나 자동 생성된 실제 **비밀번호(Passphrase)**.

> [!important] 핵심
> Ansible로 "사전에 토큰을 지정(Pre-shared Key)"할 때는 전체 문자열이 아니라 **뒤쪽의 `<SECRET>` 부분만** 입력해야 한다.

### 해결
```yaml
# ✅ 올바른 설정 — ::server: 뒤 순수 비밀번호만
k3s_token: "3ee51003c8b86d11d904ca84d28da7a5"
```
이렇게 하면:
1. **Master**가 이 문자열을 초기 비밀번호로 K3s 시작.
2. K3s가 CA 인증서를 생성하고 해시값(`K10...`)을 자동 계산해 앞부분에 붙임.
3. **Worker**가 Ansible이 주입한 이 비밀번호로 마스터에 join 요청.

### 요약 / 교훈
- **Full Token**: `K10...::server:PASSWORD` (이미 구축된 서버에서 확인되는 값, CA 검증 포함).
- **Config Token**: `PASSWORD` (설정 파일이나 `K3S_TOKEN` 환경변수에 넣어야 하는 값).
- 이미 구축된 클러스터에 수동으로 노드 추가 시엔 full token을 `k3s agent --token`에 넣어도 동작하는 경우가 있다(CA 검증용). 하지만 **초기 Bootstrapping을 위해 설정 파일/변수에 할당할 때는 순수 비밀번호만**.
- 💡 Ansible Vault로 이 토큰 값을 암호화 저장하는 것을 잊지 말 것.

### Ansible Playbook 예시

**`inventory.yml` (변수 설정)** — `k3s_token`에 `K10...`이 아닌 순수 비밀번호만:
```yaml
all:
  children:
    k3s_cluster:
      vars:
        # [중요] 'K10::...' 형식이 아닌 순수 비밀번호 문자열만. 운영에선 ansible-vault 암호화.
        k3s_token: "3ee51003c8b86d11d904ca84d28da7a5"
        k3s_version: "v1.28.5+k3s1"
    master:
      hosts:
        server-node-1: { ansible_host: 192.168.1.10 }
    worker:
      hosts:
        agent-node-1: { ansible_host: 192.168.1.11 }
        agent-node-2: { ansible_host: 192.168.1.12 }
```

**`site.yml` (Playbook)** — Master 초기화 → Worker join:
```yaml
---
- name: K3s Cluster Bootstrap
  hosts: k3s_cluster
  become: yes
  gather_facts: yes
  tasks:
    - name: K3s 설치 스크립트 다운로드
      get_url: { url: https://get.k3s.io, dest: /tmp/k3s_install.sh, mode: '0755' }

# 1. Master(Server) 노드
- name: Setup Master Node
  hosts: master
  become: yes
  tasks:
    - name: Master 노드에 K3s 설치 및 실행
      shell: /tmp/k3s_install.sh
      environment:
        K3S_TOKEN: "{{ k3s_token }}"            # 여기서 정의한 토큰이 초기 비밀번호
        INSTALL_K3S_VERSION: "{{ k3s_version }}"
        INSTALL_K3S_EXEC: "server --cluster-init"
      args: { creates: /usr/local/bin/k3s }     # 이미 설치돼 있으면 skip (멱등성)

# 2. Worker(Agent) 노드
- name: Setup Worker Nodes
  hosts: worker
  become: yes
  tasks:
    - name: Master 노드의 IP 확인 (첫 마스터 기준)
      set_fact:
        master_ip: "{{ hostvars[groups['master'][0]]['ansible_host'] }}"
    - name: Worker 노드를 클러스터에 Join
      shell: /tmp/k3s_install.sh
      environment:
        K3S_TOKEN: "{{ k3s_token }}"            # Master와 동일한 토큰(순수 비밀번호)
        K3S_URL: "https://{{ master_ip }}:6443"
        INSTALL_K3S_VERSION: "{{ k3s_version }}"
      args: { creates: /usr/local/bin/k3s }
```
> **핵심**: `K3S_TOKEN`에 `K10::...` 형식을 넣었다면 Master가 기대하는 시크릿과 달라 **403 Forbidden**이 났을 것. `args: creates: /usr/local/bin/k3s`로 멱등성 확보.
> 참고: [k3s-io/k3s-ansible](https://github.com/k3s-io/k3s-ansible) · [timothystewart6/k3s-ansible](https://github.com/timothystewart6/k3s-ansible)

## 2. K3s 서버 노드의 TLS SAN 확인 / 추가 / 회전

K3s 서버 serving 인증서의 SAN은 `kube-system/k3s-serving` 시크릿의 **annotation**(`listener.cattle.io/cn-*`, `listener.cattle.io/san-*`)으로 관리된다. 기본 SAN엔 서버 자기 IP + `kubernetes.default.svc` 클러스터명이 자동 포함.

### Method 1: `kubectl` (권장)
`metadata.annotations` 아래 SAN 확인:
```bash
kubectl get secret -n kube-system k3s-serving -o yaml
```
```yaml
metadata:
  annotations:
    listener.cattle.io/cn-10-0-0-1: 10.0.0.1
    listener.cattle.io/san-example-com: example.com
```

### Method 2: 인증서 파일 직접
control-plane 노드에서:
```bash
sudo openssl x509 -in /var/lib/rancher/k3s/server/tls/serving-kube-apiserver.crt \
  -text -noout | grep -A1 "Subject Alternative Name"
# dynamic-cert.json 이 있으면 그것도 가능:
# sudo openssl x509 -in /var/lib/rancher/k3s/server/tls/dynamic-cert.json -text -noout | grep -A1 "Subject Alternative Name"
```

### TLS SAN 추가 + 회전
```bash
# 1) 시크릿 편집 — metadata.annotations에 새 SAN 추가 (예: cn-192.168.1.100: 192.168.1.100)
kubectl edit secret -n kube-system k3s-serving
# 2) 인증서 회전
sudo k3s certificate rotate
# 3) K3s 재시작
sudo systemctl restart k3s
```

### 검증 / 만료 확인
```bash
curl -vk https://<YOUR_IP>:6443/ping     # 특정 IP/DNS가 SAN에 유효한지
sudo k3s certificate check               # 전 인증서 만료일
```
