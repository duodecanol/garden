# Findings — mise vs proto vs aqua

> 1차 실행 결과. ARM64 Docker(ubuntu:24.04) 기준. Apple Silicon 호스트.

## TL;DR

- **풀스택 모노레포(python+go+bun+terraform+uv) → mise**. 5/5 zero-config built-in, 모던 Python 생태계(uv) 통합 가장 깊음(`python.uv_venv_auto`, `python.compile=false`). 디렉터리 오버라이드 "set and forget" 자동 동작.
- **인프라 CLI 모음(terraform/kubectl/gh/awscli/uv) → aqua**. 단일 바이너리만 다루는 설계라 가볍고 빠르지만, **두 가지 실패 모드(silent registry skip / loud 404 + shim phantom)** 존재. 운영상 "shim 있다 ≠ 도구 깔려있다" 트랩에 주의. 부트스트랩이 sigstore 의존이라 막힌 망에서 깨짐.
- **메이저 런타임 위주(node/python/go/bun) → proto**도 가능. 단 terraform/uv 같은 단일 binary CLI는 community plugin URL 의존이 추가되고 디렉터리 오버라이드가 lazy-install되지 않음(`PROTO_AUTO_INSTALL=true` 필요). mise보다 ergonomic gap이 분명함.

## Cold install time (Ubuntu 24.04, ARM64 / Apple Silicon)

| Manager | python 3.12 | go 1.23 | bun 1.1.30 | terraform 1.9.0 | total wall | 비고 |
|---|---|---|---|---|---|---|
| mise | astral-sh prebuilt (`install_only_stripped`) | prebuilt | prebuilt | prebuilt | **12.45s** (4개 병렬) | python 빌드 의존성을 apt로 깔았지만 결국 안 씀 |
| proto | astral-sh prebuilt (`install_only`, 동일 소스) | prebuilt | prebuilt | n/a (built-in 미지원) | **13s** (3개 병렬, python이 13s로 max) | bun 5s, go 7s, python 13s 개별 |
| aqua | n/a (설계 외) | prebuilt(GitHub release) | ❌ silently skipped | prebuilt | **6.06s** (2개만 실설치) | bun 누락은 install 로그에 줄 자체가 없고 exit 0 |

mise/proto 둘 다 python을 소스 빌드 안 하고 astral-sh의 `python-build-standalone` 동일 소스를 사용. → "mise가 빠른 이유"가 mise만의 장점이 아니라 prebuilt 사용 덕분이라는 점 확인.

## 활성화 방식

| Manager | `which python` 결과 | shim 개수 (관찰) | 셸 통합 방식 |
|---|---|---|---|
| mise | `/root/.local/share/mise/shims/python` | 20+ — 도구별+버전별(`python`, `python3`, `python3.11`, `python3.12`, `pip`, `pip3.11`, `pip3.12`, `2to3-3.11/3.12`, `idle3.11/12`, `pydoc3.11/12` 등) | `mise activate` (PATH 변형) **또는** shim PATH 직접 추가 (이번 비교에서 채택) |
| proto | `/root/.proto/shims/python` | 7 (`bun`, `bunx`, `go`, `gofmt`, `pip`, `python` + `registry.json`) | `~/.proto/shims` PATH 추가 (디폴트) |
| aqua | `/root/.local/share/aquaproj-aqua/bin/terraform` | 3 (`go`, `gofmt`, `terraform`) | bin 디렉터리에 aqua-proxy 심볼릭 링크 |

**mise만 버전별 shim을 추가로 만듦** — 디렉터리 오버라이드 없이 `python3.11` 직접 호출 가능. proto/aqua는 단일 entrypoint per tool.

| Manager | 동작 | 비고 |
|---|---|---|
| mise | ✅ 자동 — `python --version` → `Python 3.11.15` | `mise install`이 트리 내 모든 `.mise.toml`을 스캔해 3.11도 root install 시점에 받아둠. shim도 `python3.11` 별도 생성. |

## 도구 커버리지 — 5개 타깃에 대한 매니저별 처리 (실측)

| Tool | mise | proto | aqua |
|---|---|---|---|
| python (CPython runtime) | ✅ 3.12.13 (astral-sh prebuilt) | ✅ 3.12.13 (동일 prebuilt) | ❌ 설계 외 (CLI binary installer라 런타임 미지원) |
| go | ✅ 1.23.12 | ✅ 1.23.12 | ✅ 1.23.0 |
| bun | ✅ 1.1.30 | ✅ 1.1.30 | ❌ **arm64에서 가용 불가** (registry/binary 처리 결함, 4번 iteration 후 결론) |
| terraform | ✅ 1.9.0 | ❌ **community plugin 필요** (built-in 미지원) | ✅ 1.9.0 |
| **uv** (astral-sh 단일 정적 binary, python과 별개) | ✅ 0.4.20. 추가로 mise는 **uv 전용 통합** — `python.uv_venv_auto = true`로 디렉터리 자동 venv, `python.compile = false`로 cpython 책임을 uv에 위임하는 모드. | ❌ **community plugin 필요** (terraform과 동일) | ✅ 0.4.20 (단, 첫 시도에서 `v` prefix 태그 표기 오류로 404 → `0.4.20`로 수정 후 동작) |

**최종 스코어** (수정 4회 후): mise **5/5**, proto **3/5**, aqua **3/5** (terraform, go, uv).

bun on linux/arm64은 aqua 자체의 알려지지 않은 호환 결함으로 추정 — 4번 iteration(registry v4.235→v4.506, bun 1.1.30→1.3.13→1.0.36) 모두 실패. mise/proto는 같은 컨테이너에서 자명하게 동작.

proto/aqua의 부족분은 부분적으로 설계 외 영역, 부분적으로 운영상 결함:
- proto: 메이저 런타임만 다루는 게 디자인 → terraform/uv는 community plugin 영역 (명시적 한계)
- aqua: 단일 binary CLI installer가 디자인 → python은 영영 안 됨 (명시적 한계), bun on arm64는 **사실상 깨짐** (운영상 결함)

**Python 생태계 관점에서의 의미** — 모던 Python 워크플로우가 `uv`로 이동 중인데, 매니저별 차이가 그대로 드러남:
- **mise**가 가장 깊이 통합 (uv를 도구로 깔 뿐 아니라 mise 내부에서 uv에게 cpython/venv 책임을 양보하는 모드 제공)
- **aqua**는 "도구 깔기"만은 가장 깔끔 (단일 정적 binary 제일 잘 다룸)
- **proto**는 둘 다 미흡 — built-in 커버리지 좁음

**meaning(전체)** — 풀스택 모노레포(python+go+bun+terraform+uv)를 zero-config + 외부 plugin 의존 없이 다 다루는 건 mise뿐. proto는 메이저 런타임 전용, terraform/uv/kubectl/helm 같은 CLI를 같이 쓰려면 외부 plugin URL 의존이 추가된다(또 다른 부트스트랩 리스크). aqua는 반대 축 — 인프라/CLI 도구에는 강하지만 python 같은 런타임은 구조적으로 안 됨.

## 부트스트랩(설치 자체)의 외부 의존성 — 첫 실행에서 발견

| Manager | 설치 경로 | 외부 의존 |
|---|---|---|
| mise | `curl https://mise.run \| sh` (정적 바이너리 + GitHub releases) | mise.run, GitHub |
| proto | `curl ... moonrepo.dev/install/proto.sh \| bash` | moonrepo.dev, GitHub |
| aqua | `aqua-installer` → 부트스트랩 aqua → `update-aqua` → **slsa-verifier가 rekor.sigstore.dev 조회** | GitHub + **sigstore (Rekor)** |

2026-05-05 첫 실행에서 `rekor.sigstore.dev`가 30s timeout으로 5회 retry 후 실패 → aqua 컨테이너 빌드 자체가 죽음. 우회: 공식 installer를 안 쓰고 GitHub Release 타르볼을 직접 다운로드 (`Dockerfile`의 `AQUA_VERSION` ARG).

**의미** — air-gapped/제한 네트워크 환경에서 aqua의 디폴트 설치 경로는 깨질 수 있다. mise/proto는 이런 의존이 없다. 운영 환경 선정 시 비교 축으로 쓸 만함.

## UX/출력 포맷 인상

- **mise**: one-line per step. `mise current` 출력은 4줄 텍스트, 깔끔.
- **proto**: install은 `[bun]`/`[go]`/`[python]` prefix로 다행 출력, 명확. **`proto status`는 거대한 박스 그리기에 행마다 공백 패딩이 과다** — Docker non-TTY 환경에서 특히 가독성 나쁨 (`proto.log` 35–109행 참조). TTY 환경에선 다를 수 있음.
- **aqua**: 타임스탬프 + logfmt 스타일(`INF level=...`). 운영 로깅 친화적이지만 사람 눈엔 더 읽기 어려움.

## aqua + bun + linux/arm64 — 4번 iteration해도 안 풀린 조합

bun을 aqua로 깔려고 시도한 결과(arm64 호스트, ubuntu:24.04 컨테이너):

| 시도 | registry | bun 버전 | 결과 |
|---|---|---|---|
| 1 | v4.235.0 | 1.1.30 | silent skip — install 로그에 줄 없음, exit 0 |
| 2 | v4.506.0 | 1.1.30 | `ERR ... invalid package: github_release package requires asset`, exit 1 |
| 3 | v4.506.0 | 1.3.13 (최신) | 같은 에러 |
| 4 | v4.506.0 | 1.0.36 (registry에 `supported_envs: [linux, darwin]` **명시적으로** 있는 마지막 버전) | 같은 에러 |
| 5 | v4.506.0 | 1.3.13 + **aqua 2.58.0-1 prerelease**(`feat: variants override mechanism with libc detection` PR #4733 포함) | **같은 에러** |

5번째가 결정타: aqua 2.57.2 → 2.58.0-1 사이의 새 variants/libc 메커니즘조차 이 path를 안 건드림. registry 정의 + binary 처리 + 버전 bump 어떤 축으로도 해결 안 됨 → **aqua의 yaml 파싱 또는 version_overrides 처리 로직에 linux/arm64 specific한 깊은 결함**.

4번째 케이스 보충: registry yaml에 `linux`(arm64 포함) 지원이 명시돼 있고 asset 템플릿(`bun-{{.OS}}-{{.Arch}}.{{.Format}}`)이 실제 GitHub release asset(`bun-linux-aarch64.zip`)과 정확히 매핑되는데도 aqua가 "asset 없음"으로 거부.

mise/proto는 동일 컨테이너에서 bun을 자명하게 깐다. **이 조합(aqua × bun × linux/arm64)은 운영 가용성 없음**으로 결론. 추가 조사는 비교 범위를 넘어선 aqua 내부 버그 추적이라 멈춤. 후일 aqua 2.59+ 정식 release에서 회복 여부 재방문할 가치 있음.

→ aqua.yaml에서 bun을 명시적으로 빼고 주석에 5번 시도 내역 기록. proto가 terraform을 빼는 것과 같은 맥락이지만 더 강한 근거.

## aqua의 두 가지 실패 모드 — uv 추가로 드러난 결정적 차이

uv 추가 실험에서 **bun과 uv가 정반대 방식으로 실패**:

| 케이스 | 증상 | 의미 |
|---|---|---|
| `oven-sh/bun@1.1.30` | install 로그에 줄 자체가 없음. exit 0 (uv 추가 후엔 exit 1, 그래도 bun 줄은 없음) | **registry에 패키지가 없음** → silent skip |
| `astral-sh/uv@v0.4.20` | `ERR install the package ... 404 Not Found` 명확 출력. exit 1. | **registry에는 있지만 GitHub release tag가 없음** (`v0.4.20`가 아니라 `0.4.20`이 정확한 tag) → loud failure |

→ "조용한 실패"는 registry-package 미스매치, "시끄러운 실패"는 버전-tag 미스매치. 운영상 silent 쪽이 훨씬 위험. 사용자는 install이 정상 종료한 걸로 알지만 도구가 안 깔려 있음.

### 또 하나 — shim-before-binary 디자인

uv 케이스에서 명확해짐:
```
which uv         -> /root/.local/share/aquaproj-aqua/bin/uv   ← shim 존재
uv --version     -> 404 에러                                    ← binary 다운로드 실패
```
aqua는 `aqua install` 시점에 **symlink(shim)를 binary 다운로드보다 먼저 만든다**. 다운로드가 실패해도 shim은 남음. → `which $tool`이 성공한다고 도구가 동작한다고 보면 안 됨. proto/mise는 shim과 binary가 묶여 있어 이런 패턴이 없음.

### 해결 시도 (필요 시 다음 iteration)

- aqua.yaml의 uv 버전을 `astral-sh/uv@0.4.20`(v 없이)으로 변경
- bun은 registry version을 `v4.290.0+`로 bump하거나 `aqua g oven-sh/bun@1.1.30`로 사전 검증

## 결론

### 우리 케이스 (모노레포 = python+go+bun+terraform)

**mise 채택**.

이유:
- 4개 모두 zero-config built-in
- 디렉터리 오버라이드가 자동 (서브디렉터리 진입 즉시 동작)
- 부트스트랩 외부 의존이 mise.run + GitHub만 (proto의 community plugin URL, aqua의 sigstore 의존 없음)
- 출력이 깔끔하고 silent failure 사례 없음

### 도구 카테고리별 일반 권고

| 케이스 | 권고 |
|---|---|
| 풀 런타임 + 인프라 CLI 혼합 모노레포 | **mise** 단독 |
| 메이저 런타임만(node/python/go/bun), 인프라 CLI 없음 | mise 또는 proto. 둘 다 무난, mise가 ergonomic 우위 |
| 인프라 CLI 도구 묶음(terraform/kubectl/helm/awscli) 핀만 | **aqua** 단독 (단, registry 버전 sensitivity 주의) |
| 막힌 사내망/air-gapped 환경 | **mise** (sigstore 의존 없음). proto도 가능하지만 community plugin URL 호스트 화이트리스트 필요 |

### 비고 — 추가 검증할 항목

- aqua의 bun silent skip — registry 버전 bump로 재현 여부
- proto의 `PROTO_AUTO_INSTALL=true` 모드에서 디렉터리 오버라이드가 mise처럼 자연스러워지는지
- mise의 `python3.11` 별도 shim이 venv 생성 등 실제 워크플로우에서 얼마나 유용한지 (지금은 "있다"만 확인)
